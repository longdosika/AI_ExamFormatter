# แผนผังความสามารถระบบ AI Exam Formatter

เอกสารนี้เป็นบัญชีความสามารถของระบบฉบับภาษาไทย จัดกลุ่มตามลำดับการใช้งานจริง ตั้งแต่รับไฟล์ต้นฉบับจนถึงส่งออกเอกสาร ข้อมูลมาจากโค้ดจริง เอกสารใน Knowledge Vault และหลักฐานการทดสอบที่มีอยู่ใน repository

เอกสารนี้มีหน้าที่สองอย่าง:

1. ใช้อธิบายว่าแต่ละฟังก์ชันทำอะไรและอยู่ตรงไหนในกระบวนการ
2. ใช้เป็นทะเบียนติดตามข้อจำกัดและงานที่ยังต้องพิสูจน์จากไฟล์จริง โดยเฉพาะหัวข้อ **สิ่งที่ระบบยังไม่ควรถูกเข้าใจว่า “รับประกันแล้ว”**

เอกสารนี้ไม่ใช่คำรับรองว่า OCR, การอ่านเฉลย หรือการตัดรูปจะแม่นยำกับเอกสารทุกชนิด

## สถานะที่ใช้ในเอกสาร

- **มีในระบบ**: มี implementation และมี regression หรือ browser evidence ตามขอบเขตที่ระบุ
- **ขึ้นกับ provider/configuration**: โค้ดรองรับแล้ว แต่ผลจริงขึ้นกับ API key, model, quota, endpoint หรือการตั้งค่าเครื่อง
- **ต้องตรวจจากไฟล์จริง**: มีเส้นทางรองรับ แต่ยังไม่ควรเหมารวมว่าใช้ได้กับเอกสารทุกลักษณะ
- **ยังค้าง**: มีข้อจำกัดหรือหลักฐานไม่พอ ต้องเปิดงานและบันทึกผลก่อนปิด

## ลำดับการทำงานของระบบ

```text
นำเข้าไฟล์
  -> แสดงต้นฉบับฝั่งซ้าย
  -> อ่าน OCR หรือใช้ text layer
  -> เก็บ OCR ดิบแยกตามหน้า
  -> normalize และตรวจโครงสร้าง
  -> แก้ข้อความ OCR
  -> แปลงเป็นข้อสอบ
  -> สกัดรูป/ตาราง/แผนภาพ
  -> อ่านเฉลยจากต้นฉบับ
  -> แก้ไขและตรวจฉบับแก้ไข
  -> ส่งออก Google Docs / Google Drive
```

ตำแหน่งหน้าจอปัจจุบัน:

- **ซ้าย**: ไฟล์ต้นฉบับเท่านั้น ใช้ดู เทียบ ซูม และ capture
- **ขวา**: OCR ดิบ การแปลงรูปแบบ editor การตรวจเฉลย การตรวจฉบับแก้ไข และ export

## 1. การนำเข้าไฟล์ต้นฉบับ

### ฟังก์ชัน

- ลากไฟล์มาวาง
- กดเลือกไฟล์จากเครื่อง
- ตรวจนามสกุลและขนาดไฟล์
- แสดงสถานะกำลังอ่าน/อ่านสำเร็จ/อ่านไม่สำเร็จ
- รองรับ PDF, DOCX, PNG, JPG, Markdown และ HTML
- ขนาดไฟล์ตามสัญญาปัจจุบันไม่เกิน 50 MB
- แยกเส้นทางเอกสารที่มี text layer ออกจากเอกสารสแกน
- แตกข้อความและรูปภาพจาก DOCX
- ตรวจไฟล์ DOCX ที่ไม่มี `document.xml`
- ปฏิเสธไฟล์ที่แตกหรือ render ไม่ได้พร้อมข้อความผิดพลาด

### พฤติกรรมตามชนิดไฟล์

- **PDF มี text layer**: อ่านข้อความตามตำแหน่งและบรรทัด
- **PDF สแกน**: render หน้าเป็นภาพแล้วส่ง OCR
- **PNG/JPG**: ส่งภาพเข้า OCR โดยใช้ data URL ที่ระบบจัดการเอง
- **DOCX**: อ่าน XML text runs และดึง embedded images
- **Markdown/HTML**: ใช้เป็นข้อความตั้งต้นเพื่อเข้าสู่ parser
- **ไฟล์ที่อ่านไม่ได้หรือ OCR ว่าง**: เปิดแบบร่างให้ผู้ใช้ตรวจและพิมพ์เอง ไม่สร้างข้อสอบปลอม

### ข้อควรระวัง

- PDF ที่มีขนาดใหญ่มากหรือภาพความละเอียดสูงอาจใช้ทรัพยากรมาก
- การรับไฟล์สำเร็จไม่ได้แปลว่าข้อสอบจะถูก parse ครบ
- การตรวจ source fidelity ต้องเทียบกับต้นฉบับจริง

## 2. พื้นที่ต้นฉบับและการเทียบย้อนกลับ

ฝั่งต้นฉบับเป็นพื้นที่อ่านอย่างเดียว แยกจาก editor อย่างชัดเจน

รองรับ:

- แสดง PDF ทีละหน้า
- แสดงรูปต้นฉบับความละเอียดสูง
- ปุ่มเลขหน้า
- ปุ่มก่อนหน้า/ถัดไป
- แสดงหน้าปัจจุบันและจำนวนหน้าทั้งหมด
- กระโดดจากข้อใน editor ไปยังหน้าต้นฉบับ
- ใช้ต้นฉบับตรวจข้อความ OCR
- ใช้ต้นฉบับตรวจรูปที่ AI หรือผู้ใช้ capture
- ใช้ต้นฉบับตรวจเครื่องหมายเฉลย
- ใช้ต้นฉบับเป็นหลักฐานก่อน export

เมื่อเปิด draft ที่ไม่มีไฟล์ต้นฉบับ ระบบจะแสดงพื้นที่แจ้งให้นำเข้าไฟล์ต้นฉบับใหม่ แทนการนำ OCR ไปแสดงเป็นต้นฉบับ

## 3. OCR และ provider

### Provider ที่รองรับตามการตั้งค่า

- Typhoon OCR แบบ remote
- Typhoon OCR ผ่าน Ollama ในเครื่อง
- LM Studio แบบ OpenAI-compatible
- Google Cloud Vision OCR ตามเส้นทางที่ตั้งค่าไว้
- Provider OpenAI-compatible ที่ส่งผลตาม OCR contract

ค่าที่เกี่ยวข้องอยู่ใน `.env.local` โดยไม่ควร commit secret:

```env
TYPHOON_OCR_API_KEY=
TYPHOON_OCR_BASE_URL=
TYPHOON_OCR_MODEL=
TYPHOON_OCR_CONCURRENCY=1
GEMINI_API_KEY=
GEMINI_ANSWER_MODEL=gemini-3.8-flash
```

### การอ่านหลายหน้า

- แบ่ง PDF ที่เกิน 10 หน้าเป็น batch ไม่เกิน 10 หน้าอัตโนมัติ
- รักษาเลขหน้าต้นฉบับเมื่อรวมผลกลับ
- แสดง progress ตามจำนวนหน้าจริง
- เก็บข้อความของ batch ก่อนหน้าไว้เมื่อ batch หลังล้มเหลว
- จำกัดจำนวน request พร้อมกันด้วย FIFO queue
- ค่าเริ่มต้น local หนึ่งช่อง และ remote สองช่องตาม provider
- retry เฉพาะข้อผิดพลาดชั่วคราว เช่น 429/502/503 ตาม policy
- ตรวจ upload epoch เพื่อไม่ให้ผลไฟล์เก่าทับไฟล์ใหม่
- แจ้ง busy/error แบบอ่านได้แทนการแสดงข้อความ JSON ดิบ

### สถานะระหว่าง OCR

- ไอคอน scanning
- หน้าที่กำลังประมวลผล
- จำนวนหน้าที่เสร็จ/ทั้งหมด
- สถานะอ่านไม่ครบ
- สถานะต้องตรวจ
- ข้อความ OCR ดิบสำหรับแก้ไข

## 4. OCR ดิบ, normalization และ validation

ระบบแยก OCR ออกจากการจัดรูปแบบเป็นสามชั้น

### OCR Raw

เก็บข้อมูลแยกตามหน้า:

- raw text
- source page
- provider/model
- error ของหน้า
- สถานะประมวลผล
- ลำดับและ offset ของข้อความ

### Normalization

รองรับการซ่อมรูปแบบที่ไม่เปลี่ยนความหมาย เช่น:

- `1 .` เป็น `1.`
- `ก .` เป็น `ก.`
- ช่องว่างภาษาไทยจาก OCR
- HTML escape
- Markdown/HTML wrapper ที่ provider ส่งมา
- บรรทัดที่ถูกตัดผิด

### Validation

ตรวจ:

- เลขข้อหายหรือซ้ำ
- ตัวเลือกไม่ครบ
- ตัวเลือกซ้ำ
- ป้ายตัวเลือกผิดรูปแบบ
- หน้า OCR ไม่ครบ
- ตารางหรือบริบทที่ต้องตรวจด้วยต้นฉบับ

ข้อความที่ไม่ผ่าน validation จะอยู่ใน raw review และไม่ควรถูกส่งออกเป็นผลลัพธ์ที่ดูสมบูรณ์

## 5. Parser แปลงข้อความเป็นข้อสอบ

### เลขข้อ

- `1.`
- `1)`
- `ข้อ 1`
- เลขข้อที่มีช่องว่างจาก OCR
- เลขข้อต่อเนื่องข้ามหน้า
- section ที่เริ่มเลขใหม่
- ชุดข้อสอบหลายชุดในไฟล์เดียว

### ตัวเลือก

- `ก. ข. ค. ง.`
- `ก) ข) ค) ง)`
- `A. B. C. D.`
- `1. 2. 3. 4.`
- ตัวเลือกตัวเลขอยู่บรรทัดเดียวกัน
- ตัวเลือกที่ OCR แยกเป็นหลายบรรทัด
- ตัวเลือกที่เป็นรูปภาพล้วนและไม่มีข้อความ

### การแยกขั้นตอนออกจากข้อใหม่

ระบบไม่ถือเลขที่อยู่ใน stem เป็นข้อใหม่ทันที เช่น:

```text
1. ระบายน้ำ
2. กรอง
3. ระเหย
```

ระบบดู lookahead และชุดตัวเลือกประกอบก่อนเริ่มข้อใหม่ เพื่อไม่ให้ขั้นตอนการทดลองกลายเป็นข้อสอบปลอม

### รูปแบบพิเศษ

- โจทย์หลายคอลัมน์
- choice แบบ inline เช่น `1..2` และ `3..4`
- ตารางที่มี label/value
- ตารางที่ใช้เป็นข้อมูล stem
- คำอธิบายที่มีเลขลำดับภายใน
- `[รูปต้องตรวจสอบ]` ที่ต้องผูกกับ source page
- เอกสารยาว 80 ข้อหรือมากกว่า

---

## 6. โจทย์ร่วมและข้อมูลใช้ร่วมกัน

ระบบตรวจหัวข้อ เช่น:

```text
ใช้ข้อมูลในตารางต่อไปนี้ตอบคำถามข้อ 17-18
```

แล้วสร้างโครงสร้าง:

1. หัวข้อโจทย์ร่วม
2. ข้อความนำ
3. รูป/ตารางโจทย์ร่วม
4. ข้อย่อยที่เกี่ยวข้อง
5. ตัวเลือกของแต่ละข้อ
6. `จบโจทย์ร่วม`

ความสามารถที่เกี่ยวข้อง:

- เก็บข้อความนำก่อนข้อแรก
- ไม่ตัดข้อมูลระหว่างข้อ
- ผูกตารางกับช่วงข้อ
- ไม่แสดงข้อความตารางซ้ำเมื่อมีภาพตารางแล้ว
- แสดงสีและลำดับตามแม่แบบ

## 7. Capture รูปภาพแบบผู้ใช้ลากกรอบ

ผู้ใช้กดไอคอน capture แล้วลากกรอบบนต้นฉบับเพื่อเลือกพื้นที่

ขั้นตอน:

1. เปิดโหมด capture
2. ลากกรอบบนภาพ/PDF
3. ดูขนาดพื้นที่ที่เลือก
4. เลือกข้อปลายทาง
5. เลือกบทบาทของรูป
6. ถ้าเป็นรูปตัวเลือก ให้เลือก ก/ข/ค/ง หรือ key ที่ใช้งาน
7. ตรวจ preview
8. กดแทรกภาพ

บทบาทที่เลือกได้:

- รูปโจทย์
- รูปโจทย์ร่วม
- รูปตัวเลือก
- รูปคำอธิบาย

การ capture แบบนี้ไม่ต้องมีเส้นกรอบในต้นฉบับ ผู้ใช้จึงใช้ได้กับรูปที่ลอยอยู่บนหน้า รูปวาด กราฟ สมการ หรือแผนภาพไม่มีขอบ

---

## 8. Capture ตารางและรูปแบบขอบต่าง ๆ

### ตารางมีกรอบชัด

รองรับ:

- ตารางเส้นเต็ม
- ตารางหลายคอลัมน์
- ตารางหัวตาราง
- ตาราง merged cell
- ตารางข้อมูลการทดลอง
- ตารางคำตอบ
- ตารางที่ใช้ร่วมกับหลายข้อ

ระบบพยายามรักษา:

- เส้นบนและเส้นล่าง
- หัวตาราง
- cell สุดท้าย
- label ของคอลัมน์
- ระยะปลอดภัยรอบตาราง

### ตารางไม่มีกรอบ

ใช้ manual capture ได้โดยไม่ต้องมีเส้นขอบ ระบบไม่บังคับให้ Vision ต้องหา outer border ก่อน

### ตารางเส้นจางหรือเส้นไม่ครบ

ระบบมี safe margin และ gutter trimming ช่วยกรณี:

- เส้นบาง
- เส้นจาง
- ขอบหายบางด้าน
- ตารางเอียงเล็กน้อย
- ข้อความชิดขอบ
- ข้อความด้านบน/ล่างอยู่ใกล้ตาราง

ระบบไม่ได้วาดเส้นตารางที่หายขึ้นมาใหม่ หาก Vision มองไม่เห็นตาราง ผู้ใช้ต้องตรวจภาพหรือใช้ manual capture

### ตารางติดข้อความของข้ออื่น

smart trimming พยายามตัด:

- ตัวเลือกของข้อก่อนหน้าที่อยู่เหนือภาพ
- โจทย์ของข้อถัดไปที่อยู่ใต้ภาพ
- หัวข้อที่อยู่ด้านบน
- ตัวเลือกที่อยู่ด้านล่าง
- เศษข้อความจาก gutter ด้านซ้าย/ขวา

การตัดใช้การตรวจ text band และช่องว่าง ไม่ได้ยึด offset ตายตัวเพียงอย่างเดียว

## 9. Capture รูปโจทย์ที่ไม่มีกรอบและรูปอุปกรณ์

### รูปไม่มีกรอบ

เหมาะกับ:

- กราฟ
- แผนภาพ
- สมการ
- รูปวาด
- รูปลอยบนพื้นขาว
- รูปที่มีข้อความรอบด้าน

AI อาจหา bounding box ได้ แต่ manual capture เป็นเส้นทางสำรองที่เชื่อถือได้กว่าเมื่อรูปไม่มีขอบชัด

### รูปอุปกรณ์ทดลอง

ระบบพยายามเก็บทั้งภาพและข้อความกำกับ:

- อุปกรณ์หลัก
- ฐาน
- ลูกศร
- leader line
- label ด้านขวา
- label ด้านซ้าย
- คำว่า “สารละลายส่วนบน”
- คำว่า “สารละลายส่วนล่าง”

มีการเพิ่ม horizontal padding และ bottom padding เพื่อไม่ให้คำกำกับปลายประโยคถูกตัด

## 10. AI Diagram Harvesting

หลังแปลงข้อสอบ ระบบมีขั้นสกัดภาพด้วย AI แยกจาก OCR และ parser

AI พยายามหา:

- ตาราง
- รูปโจทย์
- รูปโจทย์ร่วม
- รูปตัวเลือก
- รูปเครื่องมือทดลอง
- รูปกราฟ
- รูปแผนผัง
- รูปคำอธิบาย
- รูปเฉลย

ผลลัพธ์แต่ละภาพควรมี:

- question id
- source page
- bounding box
- image role
- confidence/metadata ที่ provider ส่ง

ถ้าผล AI ไม่แน่ใจ ผู้ใช้ยังสามารถ capture เองได้ และภาพที่ยังไม่ได้ตรวจจะไม่ควรถูกถือว่าเป็นผลสมบูรณ์

## 11. รูปตัวเลือกและตัวเลือกที่เป็นภาพล้วน

รองรับกรณี:

- ตัวเลือกเป็นข้อความ
- ตัวเลือกเป็นภาพ
- ตัวเลือกไม่มีข้อความเลย
- รูปผลึก 1–4
- รูปกราฟหลายตัวเลือก
- รูปแผนภาพที่ต้องผูกกับ choice key

ระบบไม่ควรติด caption `รูปโจทย์:` ให้ภาพตัวเลือก ปัจจุบัน label สำหรับภาพจะถูกจัดตามบทบาทเพื่อลดการแสดงซ้ำ

## 12. การจัดรูปแบบข้อสอบ

ระบบจัดรูปแบบตามแม่แบบ QuizFlow/Design Constitution:

- ฟอนต์ Sarabun
- ขนาดมาตรฐาน 12 pt
- เลขข้อเด่นและหนา
- สีเลขข้อและสถานะตาม design token
- หัวข้อสี teal
- shading สำหรับหลักฐานเฉลย
- การขึ้นบรรทัดของขั้นตอน
- ระยะห่างระหว่าง stem และตัวเลือก
- เส้นใต้ label ตารางก่อน colon โดยไม่ทำลายข้อความ value
- shared context พร้อมจุดเริ่ม/จบ
- รูปอยู่ในลำดับที่ตรวจจากต้นฉบับ

ระบบใช้ explicit conversion ผู้ใช้สามารถแก้ OCR ก่อนกดแปลงได้ และการแปลงไม่เรียก OCR ใหม่

## 13. การอ่านเฉลยจากต้นฉบับ

### เฉลยที่เป็นข้อความ

รองรับ:

- `คำตอบ: ก`
- `เฉลย: ข`
- `Answer: C`
- colon ปกติ
- colon แบบเต็มความกว้าง
- explanation ที่ระบุ key ชัดเจน
- เครื่องหมายดาวหรือ shading ที่ parser รู้จัก

### เฉลยจากภาพด้วย Gemini

Gemini ใช้เพื่ออ่านหลักฐานที่มีอยู่ในภาพ เช่น:

- วงกลมของครู
- กากบาทของครู
- เครื่องหมายถูก
- การขีดทับตัวเลือก
- การเน้นตัวเลือก

กฎสำคัญ:

- อ่านเฉลยที่มีอยู่ ไม่แก้โจทย์เพื่อหาคำตอบ
- ตรวจว่าตรงกับข้อและตัวเลือกจริง
- ปฏิเสธ key ที่ไม่ถูกต้อง
- ปฏิเสธผลซ้ำหรือขัดแย้ง
- ความมั่นใจต่ำให้คงเป็น “ต้องตรวจ”
- ไม่มีเครื่องหมายให้เว้นว่าง
- เก็บหลักฐาน source page และบริเวณภาพ

โมเดลที่แสดงในรายการไม่ได้รับประกันว่า generateContent ใช้งานได้ ต้องทดสอบ request จริงกับ key และ quota ของเครื่องนั้น

## 19. Local, Vercel และความปลอดภัย

### Local

- bootstrap ด้วย PowerShell
- ตรวจ environment ก่อนเริ่ม
- ใช้ Ollama ได้
- ใช้ Typhoon remote ได้
- ใช้ Gemini แยกจาก OCR ได้
- ใช้ Google OAuth local ได้เมื่อ redirect ตรง
- build stamp เปลี่ยนตาม build/dev pass

### Vercel

- มี `vercel.json`
- ตั้ง max duration สำหรับ route ที่ใช้ OCR/Vision/export
- bundle PDF.js worker และ assets ไว้ใน repository
- ต้องใส่ production environment variables
- `localhost` ของ notebook ใช้จาก Vercel ไม่ได้

### Security

- ไม่ commit `.env.local`
- ไม่แสดง API key ใน UI หรือ log
- รองรับ key สำรองสำหรับ quota exhaustion
- หมุน key เฉพาะ 429/403 ที่เป็น quota ตาม policy
- error จาก request ผิดรูปแบบไม่ควรถูกกลบด้วย key rotation

### กฎการปิดรายการในทะเบียนข้อ 20

แต่ละรายการต้องมีอย่างน้อย:

1. ไฟล์ต้นฉบับหรือ hash ที่ตรวจซ้ำได้
2. ผลลัพธ์จากระบบที่บันทึกไว้
3. ภาพหรือ JSON หลักฐานใน `evidence/`
4. ผู้ตรวจเทียบต้นฉบับ
5. ผล regression ที่เกี่ยวข้อง
6. ระบุว่าเป็น PASS, FAIL หรือ BLOCKED
7. บันทึกปัญหาและบทเรียนใน `documents/memory.md`
8. เปิดหรือปิด Task ใน `documents/tasks.md`

- build ผ่าน
- parser test ผ่าน
- provider ตอบ HTTP 200
- model ปรากฏใน models list
- ภาพแสดงใน browser แต่ยังไม่ได้เทียบต้นฉบับ
- ระบบสร้างผลลัพธ์ได้หนึ่งไฟล์
